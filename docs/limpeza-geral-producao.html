1. O que a limpeza faz

Durante os testes, o sistema foi usado com dados fictícios: requisições, checklists, fotos, notificações, localizações, auditoria. Antes do uso real, esses dados precisam sair, para que o sistema comece limpo.

A limpeza tem duas ferramentas, sempre nesta ordem:

  1. SQL (supabase/ops/limpar_dados_de_teste.sql): colado no SQL Editor do painel do Supabase. Apaga as linhas do banco. Não mexe em arquivos.
  2. Storage (python -m app.ops.limpar_storage): rodado dentro do container do backend, na VPS. Apaga os arquivos (fotos de checklist e fotos de perfil).

As duas são seguras por padrão:

  • Começam em ensaio: mostram quantos itens seriam apagados e não apagam nada.
  • Só apagam quando você digita uma frase de confirmação exata, que inclui o identificador do projeto (ofwvoztarroglekfwohs).
  • O SQL ainda exige o número que o ensaio mostrou. Se qualquer dado mudar entre o ensaio e a execução, ele recusa.
  • O SQL roda numa transação única: ou apaga tudo, ou não apaga nada.
  • Depois do lacre (passo 11), as duas ferramentas recusam para sempre neste banco.
  • As mensagens mostram só contagens, nunca nomes, e-mails ou outros dados pessoais.
ATENÇÃO

Use somente antes do uso real. Depois que houver dados verdadeiros, nunca rode estas ferramentas. Depois da execução real não há desfazer pelo script; só o backup (passo 1) recupera.

Por que é uma exceção

O sistema normalmente proíbe apagar registros e trata a auditoria como "só acrescenta". Esta limpeza é uma exceção única, pré-lançamento, aplicada sobre dados fictícios. As proteções do banco são desligadas só durante a transação, religadas do mesmo jeito e conferidas no fim.

2. O que é apagado e o que fica

Antes de começar, escolha um dos dois modos. O modo vale para o SQL e para o Storage, e tem de ser o mesmo no ensaio e na execução.

  • Modo A, manter usuários (padrão): as contas criadas nos testes já são das pessoas reais e devem continuar.
  • Modo B, só admins: as contas de teste devem sumir; ficam só os administradores ativos. Os usuários reais são convidados depois.

3. Checklist do que preparar

Marque cada item antes do passo 1.

  • Acesso ao painel do Supabase do projeto ofwvoztarroglekfwohs, com permissão de dono (SQL Editor e Database > Backups).
  • Acesso à VPS (terminal na pasta do projeto) para rodar git pull e docker compose.
  • Quem mantém o sistema disponível para rodar o supabase db push pelo pipeline (passo 2).
  • Modo escolhido: A (manter usuários) ou B (só admins). Anote aqui: ______
  • No modo B: pelo menos 1 admin real ativo, que consegue entrar no sistema.
  • Horário sem uso do sistema (avise os usuários). O backend ficará parado alguns minutos.
  • Backup recente disponível ou forma de fazer uma cópia do banco.
  • Papel ou bloco de notas para anotar o número do ensaio e os resultados. Ou faça capturas de tela.
  • Este guia aberto e o arquivo supabase/ops/limpar_dados_de_teste.sql à mão (do repositório atualizado).
Dica

Faça tudo de uma vez, na ordem, sem pular passos. Se algo parecer errado em qualquer momento, pare: até o passo 6 nada foi apagado.

4. Passo a passo

1 Backup

Onde: painel do Supabase

  1. Abra supabase.com/dashboard/project/ofwvoztarroglekfwohs. Confira o ref no endereço. Se for outro projeto, pare.
  2. Vá em Database > Backups e confira se há um backup recente (backup diário só existe em plano pago).
  3. Sem backup no painel: peça a quem mantém o sistema uma cópia do banco (pg_dump/export) e guarde-a em local seguro.
Deve aparecer: um backup com data de hoje ou de ontem, ou a confirmação de que a cópia foi feita.

2 Aplicar as migrations pendentes (db push)

Onde: computador de quem mantém o sistema (pipeline). Nunca pela VPS.

supabase db push --dry-run
supabase db push

Precisam estar aplicadas, entre outras:

  • 20261127120000_km_percorrido
  • 20261128120000_perfis_telefone, 20261128120100_convites_telefone, 20261128120200_convites_telefone_expurgo
  • 20261129120000_ops_banco_lacrado (permite ao Storage conferir o lacre)
Deve aparecer: o --dry-run lista as migrations pendentes; o db push termina sem erro. Rodando o --dry-run de novo, nada fica pendente.

3 Atualizar a VPS (--build)

Onde: terminal da VPS, na pasta do projeto

git pull
docker compose up -d --build
docker compose ps

O --build é necessário porque a ferramenta de Storage vem dentro da imagem nova do backend.

Deve aparecer: no docker compose ps, backend e frontend como running e (healthy).

4 Parar o backend

Onde: terminal da VPS

docker compose stop backend

O SQL trava as tabelas por instantes (o ensaio também). Com o backend parado, ninguém grava nada no meio. O backend fica parado só durante os passos 5 e 6.

Deve aparecer: Container sisveiculos-backend-1 Stopped (o nome pode variar). O site mostra erro ao tentar entrar: é o esperado por alguns minutos.

5 Ensaio do SQL

Onde: painel do Supabase > SQL Editor

  1. Clique em SQL Editor > New query.
  2. Abra supabase/ops/limpar_dados_de_teste.sql, copie tudo e cole.
  3. Modo A: não mude nada. Modo B: mude só esta linha: 
    v_manter_usuarios  boolean := false;
  4. Clique em Run.
Deve aparecer: uma mensagem de erro que começa com ENSAIO: nada foi apagado. É assim mesmo: o ensaio usa o erro para desfazer tudo. Na mensagem:
  • *** COPIE ESTE NUMERO PARA v_confere_total: N *** (anote o N);
  • MODO: o modo escolhido e se a auditoria será apagada;
  • uma tabela com ANTES e APAGADAS por tabela;
  • MANTIDAS (nao mudam): veículos, configurações etc.;
  • CONTAS: quantos admins ativos ficam e quantas contas seriam apagadas no modo B;
  • Arquivos por bucket: quantos arquivos há (o SQL não os apaga).

Copie ou fotografe a mensagem. Confira se os números fazem sentido. Se algo parecer errado, pare e religue o backend (passo 7).

6 Execução do SQL

Onde: o mesmo SQL Editor, na mesma consulta

Mantenha o modo do ensaio e mude somente estas três linhas (N é o número do ensaio):

v_executar         boolean := true;
v_confirmacao      text    := 'FRASE DA TABELA ABAIXO';
v_confere_total    int     := N;
ModoAuditoriaFrase exata
Aapagar (padrão)APAGAR DADOS DE TESTE ofwvoztarroglekfwohs E AUDITORIA
AmanterAPAGAR DADOS DE TESTE ofwvoztarroglekfwohs
Bapagar (padrão)APAGAR DADOS DE TESTE ofwvoztarroglekfwohs E AUDITORIA E USUARIOS

Clique em Run. Se o painel avisar sobre DELETE, confirme.

Deve aparecer: nenhum erro e uma tabela de resultado com as colunas tabela, linhas, apagadas_agora e situacao:
  • 0 nas tabelas sempre apagadas (requisições, checklists, notificações etc.);
  • auditoria com 1 (ou as linhas de antes + 1, se manteve a auditoria);
  • veículos, configurações e saudações com o mesmo número do ensaio;
  • modo B: perfis e auth.users com o número de admins ativos e convites com 0.

Copie ou fotografe o resultado.

ATENÇÃO

Depois deste passo, os dados não voltam sem o backup. Não deixe v_lacrar := true a menos que esta seja a limpeza final e o lançamento seja imediato.

7 Religar o backend

Onde: terminal da VPS

docker compose start backend
docker compose ps

A ferramenta de Storage roda dentro do backend, por isso ele precisa estar no ar.

Deve aparecer: backend como running e, depois de alguns segundos, (healthy).

8 Ensaio do Storage

Onde: terminal da VPS, na pasta do projeto

Modo A:

docker compose exec backend python -m app.ops.limpar_storage

Modo B:

docker compose exec backend python -m app.ops.limpar_storage --apagar-usuarios
Deve aparecer: ENSAIO (nada foi apagado). Modo: ... e uma linha por bucket, por exemplo: 
  avatares: 12 arquivo(s); apagar 9; manter 3
  checklists: 40 arquivo(s); apagar 40; manter 0
e, no fim, Para executar: --executar e a frase "APAGAR ARQUIVOS ofwvoztarroglekfwohs". Nada é apagado. Não aparecem nomes de arquivo, links ou senhas.

Se aparecer AVISO: não foi possível ler o lacre do banco, a migration 20261129120000 não foi aplicada: volte ao passo 2.

9 Execução do Storage

Onde: terminal da VPS

O mesmo comando do mesmo modo, com --executar:

docker compose exec backend python -m app.ops.limpar_storage --executar
docker compose exec backend python -m app.ops.limpar_storage --executar --apagar-usuarios

(o primeiro para o modo A, o segundo para o modo B). Ele mostra o PLANO e pede:

Digite exatamente: APAGAR ARQUIVOS ofwvoztarroglekfwohs

Digite a frase (a mesma nos dois modos) e tecle Enter.

Deve aparecer: CONCLUÍDO. Situação atual: com apagar 0 em avatares e checklists.
ATENÇÃO

Rode o Storage sempre depois do SQL. Arquivos apagados não voltam (o backup do banco não guarda arquivos).

10 Conferência

Onde: sistema (navegador) e terminal da VPS

  1. Entre no sistema com o administrador real.
  2. A lista de requisições deve estar vazia e o veículo, livre.
  3. Modo A: confira que uma conta real consegue entrar. Modo B: só os admins existem; convide os usuários reais a partir de agora.
  4. Rode de novo o ensaio do Storage (passo 8).
Deve aparecer: apagar 0 em checklists e avatares.

É normal surgirem linhas novas em acessos de login, notificações e auditoria por causa do seu login. Por isso um novo ensaio do SQL não mostrará tudo zerado.

11 Lacre

Onde: painel do Supabase > SQL Editor > New query

O lacre faz o banco recusar as duas ferramentas daí em diante. Grave-o no lançamento, antes de entrar qualquer dado real.

  1. Cole o conteúdo de supabase/ops/lacrar_producao.sql.
  2. Mude a linha da confirmação para: 
    v_confirmacao  text := 'LACRAR PRODUCAO ofwvoztarroglekfwohs';
  3. Clique em Run.
Deve aparecer: sisveiculos:lacrado e o comentário anterior que foi substituído.

Para conferir depois (por exemplo, após restaurar um backup):

select shobj_description(oid, 'pg_database') from pg_database where datname = current_database();
Limites do lacre

Protege contra erro e esquecimento, não contra má-fé: o dono do banco pode desfazê-lo. Também pode se perder num restore de backup ou na recriação do projeto. Desfazer o lacre só antes de haver dado real, por decisão consciente do dono do banco.

12 Apagar os snippets do Studio

Onde: painel do Supabase > SQL Editor

O SQL Editor guarda as consultas usadas. Uma consulta salva com v_executar := true e a frase, rodada por engano no futuro, seria recusada pelo número e pelo lacre, mas não deixe esse risco.

  1. Na lista de consultas, abra o menu (⋯) de cada consulta usada nos passos 5, 6 e 11.
  2. Clique em Delete e confirme.
Deve aparecer: nenhuma consulta com a limpeza ou o lacre na lista do SQL Editor.

5. Erros e o que fazer

O SQL é uma transação única: qualquer erro desfaz tudo. As mensagens trazem só contagens. Em caso de dúvida, copie a mensagem inteira e envie a quem mantém o sistema.

6. O que nunca fazer

  • Nunca rode a limpeza depois que houver dados reais no sistema.
  • Nunca rode sem backup (passo 1).
  • Nunca pule o ensaio nem reaproveite o número de um ensaio antigo ou de outro modo.
  • Nunca mude outras linhas do SQL além das indicadas neste guia.
  • Nunca rode o supabase db push pela VPS nem edite arquivos na VPS: lá só git pull e docker compose.
  • Nunca rode o Storage antes do SQL.
  • Nunca apague os buckets em si, nem arquivos à mão, nem usuários pelo painel do Auth fora deste procedimento.
  • Nunca desative nem apague a conta do administrador real.
  • Nunca desfaça o lacre depois do lançamento.
  • Nunca cole senhas, chaves ou o conteúdo do .env em mensagens, prints ou no SQL Editor.
  • Nunca deixe snippets da limpeza ou do lacre salvos no Studio (passo 12).
  • Nunca force um erro de "estrutura inesperada" desligando proteções do banco: envie a mensagem a quem mantém o sistema.
